# DtdpGIS 1.0 软件框架设计文档

- 日期：2026-10-17
- 状态：已确认，待进入实现计划
- 适用范围：1.0 版本整体框架与首批批处理工具

## 1. 背景与目标

DtdpGIS 是一个面向 51WORLD GIS 数据处理工程师岗位场景的桌面批处理软件。软件以 Python 编写，GUI 使用 Qt，基础运行环境为 `D:\DtdpGIS\Python` 中从 ArcGIS Pro 克隆出的 Python 3.13 环境。

1.0 版本要达成的核心目标是：

- 输入一个或多个数据目录，自动完成数据普查、指定处理、质检和报告输出。
- 对“数据能不能用”给出明确结论：通过、警告、不通过。
- 所有工具按批处理设计，不面向单文件人工点选。
- 建立可持续扩展的工具注册机制，后续在每个模块中逐步追加工具，不修改 GUI 主干。
- 不原地覆盖用户数据，每次运行结果可追溯、可复核。

## 2. 1.0 范围

### 2.1 范围内

- L0 平台底座：项目空间、数据资产清单、简单任务编排、运行日志、HTML 报告。
- M1 数据接入与质检：多格式元数据普查、入口级可接受性质检、点云轻量统计。
- M2 坐标与基准：矢量/栅格批量重投影、CRS 审计。
- M3 矢量清洗与拓扑：拓扑修复、属性标准化。
- M4 栅格与地形：空洞/异常值修复、镶嵌与接边。
- M5 点云与倾斜摄影：LAS/LAZ 质检、地面滤波、抽稀；OSGB 坐标与质量检测按外部命令预留接口。
- M6 矢量融合与三维化：空间关系检查、建筑轮廓挤出为白模。
- M7 AI 辅助：只实现插件接口，不内置模型。

### 2.2 范围外或延后

- OSGB 转 3D Tiles 转换器本体：接入成熟外部工具，不在 1.0 自研。
- 点云语义分割、影像变化检测、陌生格式的大模型解析：作为 M7 插件，依赖独立环境。
- 3DGS、NeRF、BIM 轻量化、PostGIS 持久化：后续版本。
- 服务端任务调度、多机并发、云发布：后续版本。

## 3. 总体架构

软件分为一个平台底座和七个业务模块。业务模块按“数据处理性质”切分，不按“数据格式”切分。

```text
┌─────────────────────────────────────────────────────────┐
│                        PySide6 GUI                        │
├───────────┬───────────┬───────────┬───────────┬───────────┤
│  M1 接入  │ M2 坐标   │ M3 矢量   │ M4 栅格   │ M5 点云   │
│  与质检   │ 与基准    │ 清洗拓扑  │ 与地形    │ 与倾斜    │
├───────────┴───────────┴───────────┴───────────┴───────────┤
│              M6 矢量融合与三维化   M7 AI 插件              │
├───────────────────────────────────────────────────────────┤
│  L0 平台底座：项目空间 / 任务编排 / 日志 / 报告 / 配置 / 留痕 │
└───────────────────────────────────────────────────────────┘
```

## 4. 核心设计原则

1. 工具与界面解耦：GUI 不硬编码业务逻辑，只根据 `ToolSpec` 元数据渲染表单和结果。
2. 模块内聚、模块间松耦合：模块只通过统一的输入、输出、配置和结果对象通信。
3. 批处理优先：工具的默认输入是目录或目录列表，输出是目录加报告。
4. 可追溯：不原地写回；每次运行有唯一 `run_id`，输出目录、清单和报告可回溯。
5. 规则可配置：坐标范围、容差、阈值、字段映射等放在 YAML 配置中，不写死在代码里。
6. 干跑先行：支持 dry-run，先输出影响范围和异常清单，用户确认后再执行。

## 5. 技术栈决策

| 领域 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.13 | 使用 `D:\DtdpGIS\Python` 克隆环境 |
| GUI | PySide6 | LGPL，API 与 PyQt 基本一致 |
| 栅格 | rasterio / GDAL 3.11 | DEM、DOM、GeoTIFF |
| 矢量 | geopandas / pyogrio / shapely | 几何读取、空间操作、拓扑修复 |
| 坐标 | pyproj 3.7 | 投影转换、分带、参数转换 |
| 点云 | PDAL 3.4 | LAS/LAZ 管道化批处理 |
| 报告 | Jinja2 + matplotlib | HTML 报告与图表 |
| 配置 | PyYAML + pydantic | 配置解析与校验 |
| 状态 | SQLite | 运行记录、任务状态、断点信息 |
| 三维输出 | GeoPackage / GeoJSON 优先 | 3D Tiles 后续接入外部工具 |

安装约束：`PySide6` 只安装到克隆环境，不写入原始 ArcGIS Pro 环境。CPU 密集型工具通过 `ProcessPoolExecutor` 执行，GUI 线程只负责调度和展示。

## 6. 模块设计

### L0 平台底座

定位：项目空间、任务编排、日志、报告、配置和版本留痕。

1.0 能力：

- `ProjectWorkspace`：初始化项目目录，生成 `manifest.json`。
- `JobRunner`：简单 DAG，支持顺序、依赖、重试、跳过失败和断点续跑。
- `ReportService`：汇总检查项，生成红/黄/绿三色 HTML 报告。
- `ConfigStore`：按项目加载 YAML 质检规则。
- `RunLog`：SQLite 记录每次运行、每个任务和每个文件的结论。

扩展点：任务调度策略、报告模板、审计字段均通过接口替换。

### M1 数据接入与质检

定位：所有处理的前置关卡。负责数据普查、入口质检、异常标记和隔离区收纳。

1.0 工具：

- `inventory.batch_scan`：递归扫描目录，按格式分发到读取器，输出资产清单 CSV/JSON。
- `ingest.batch_qc`：按项目规则对全部资产执行入口级可接受性检查，输出 pass、warn、fail。
- `pointcloud.batch_stats`：批量统计 LAS/LAZ 点数、Z 分位、分类分布、点间距、CRS。

输出：`assets.json`、`assets.csv`、`qc_summary.csv`、`pointcloud_stats.csv`、`quarantine_manifest.csv`。

扩展点：新增格式读取器、陌生格式探测、质检规则插件、来源档案校验。

M1 详细功能配置见 `2026-10-17-m1-data-ingest-design.md`。

### M2 坐标与基准

定位：统一坐标基准，先审计后重投影，处理跨带和接边。

1.0 工具：

- `crs.audit`：检查 CRS 声明、范围、单位、中央经线和基准，输出 `crs_audit.csv`。
- `crs.batch_reproject_vector`：批量重投影源 CRS 明确的矢量，输出 `vector/` 和清单。
- `crs.batch_reproject_raster`：批量重投影源 CRS 明确的栅格，输出 `raster/` 和清单。

扩展点：七参数/四参数转换、按范围自动判断分带、接边吸附。

M2 详细功能配置见 `2026-10-17-m2-crs-design.md`。

### M3 矢量清洗与拓扑

定位：承接 M2 重投影后的矢量，修复几何拓扑并规范属性字段。

1.0 工具：

- `topology.batch_repair`：修复自相交、重复顶点、无效环，标记狭长面，输出修复前后对比。
- `attribute.batch_normalize`：按配置重命名字段、统一空值、校验必填字段和值域，输出规范化矢量。

扩展点：悬挂边、缝隙、面重叠、水系/路网专项拓扑规则。

M3 详细功能配置见 `2026-10-17-m3-vector-topology-design.md`。

### M4 栅格与地形

定位：承接 M2 已重投影的栅格，完成 DEM/DOM 修复、异常值处理和同类镶嵌。

1.0 工具：

- `raster.batch_fill_holes`：按 DEM/DOM/分类栅格分治，填充 Nodata 空洞并输出填充掩膜。
- `raster.batch_outlier_fix`：按邻域统计检测并修复 DEM/DOM 异常值，输出异常值掩膜。
- `raster.batch_mosaic`：按类型、CRS、分辨率分组镶嵌，检查接边质量。

扩展点：DOM 差分、局部坐标纠正、地形衍生指标。

M4 详细功能配置见 `2026-10-17-m4-raster-terrain-design.md`。

### M5 点云与倾斜摄影

定位：发布前点云处理与 OSGB Block 级质量检测。

1.0 工具：

- `pointcloud.batch_ground_filter`：PDAL `filters.csf` 地面点提取，输出地面点 LAS 和 DEM。
- `pointcloud.batch_thin`：随机或体素抽稀，默认保护地面点。
- `oblique.batch_quality_check`：OSGB Block 级悬浮、拉花、空洞、坐标和接边粗筛，只检测不修复。

扩展点：点云分类、格式转换、OSGB/3D Tiles 转换器接入、单体化流程。

M5 详细功能配置见 `2026-10-17-m5-pointcloud-oblique-design.md`。

### M6 矢量融合与三维化

定位：在 M3 标准化矢量上做跨图层空间关系检查，并把建筑规则化挤出为三维白模。

1.0 工具：

- `vector.batch_spatial_relation`：检查道路/水系重叠、水系重叠、POI 行政区归属、包含关系，只检测不修复。
- `building.batch_extrude`：按 `height/floors` 字段挤出建筑白模，输出 GeoPackage 和 GeoJSON。

扩展点：按道路等级生成附属设施、BIM 轻量化、属性映射到 3D Tiles。

M6 详细功能配置见 `2026-10-17-m6-vector-fusion-3d-design.md`。

### M7 AI 辅助插件

定位：可选 AI 能力层，通过插件目录和子进程隔离接入，不阻塞主流程。

1.0 框架能力：

- 插件发现、schema 校验、健康检查、子进程执行、超时控制和输出契约校验。
- 支持 `local_process`、`cloud_api`、`local_api`、`hybrid` 四类后端。
- 统一插件目录、`plugin.yaml`、输入输出契约和 QC 长表。

扩展点：点云语义分割、地物自动提取、影像变化检测、大模型辅助格式解析与异常排查。

M7 部署方案见 `2026-10-17-m7-ai-plugin-deployment-design.md`。

## 7. 工具扩展机制

这是 1.0 最重要的结构性设计。新增一个批处理工具只应做三件事：

1. 在对应模块包下新增一个工具模块。
2. 定义 `ToolSpec` 元数据。
3. 实现统一的 `BaseTool` 接口。

### 7.1 ToolSpec

每个工具用 `ToolSpec` 声明自身能力，GUI 根据它自动生成表单：

- `id`：稳定工具标识。
- `name` / `description`：显示名和说明。
- `module`：所属业务模块。
- `inputs`：输入文件或目录描述。
- `params`：参数 schema，含类型、默认值、校验范围。
- `outputs`：输出物描述。
- `side_effects`：是否写文件、是否只读、是否支持 dry-run。

### 7.2 BaseTool

统一接口至少包含：

- `validate(inputs, params)`：执行前校验，返回可读错误。
- `dry_run(inputs, params)`：返回影响范围、文件数和异常预览。
- `execute(inputs, params, context)`：执行批处理并返回 `ToolResult`。

### 7.3 ToolResult

统一结果对象包含：

- `status`：成功、部分成功、失败。
- `item_results`：每个文件的结论。
- `outputs`：输出目录和文件清单。
- `report_sections`：写入 HTML 报告的检查项。
- `warnings` / `errors`：人类可读问题列表。

### 7.4 注册机制

启动时扫描模块包下的工具模块，构建 `TOOL_REGISTRY`。GUI 只读取注册表，不写死工具列表。后续追加工具无需改 GUI 或 L0 平台代码。

## 8. 数据模型

核心对象：

- `DataAsset`：文件路径、格式、CRS、范围、大小、哈希、来源、状态。
- `Run`：`run_id`、开始时间、结束时间、项目、用户参数、状态。
- `Task`：一次运行中的一个工具调用，含输入、参数、输出、重试次数、状态。
- `ItemResult`：单个文件或图幅的处理结论。
- `Check`：检查项名称、阈值、实测值、等级。
- `Report`：聚合 `Run` 内所有检查项，生成 HTML。

## 9. 项目空间与数据流

项目目录结构：

```text
<project>/
  inputs/          # 原始数据只读副本或链接
  quarantine/      # 不通过质检的隔离数据
  working/         # 中间结果
  outputs/
    <run_id>/      # 每次运行独立目录
  reports/
    <run_id>.html
  profiles/
    default.yaml
  state.db         # SQLite 运行状态
```

标准数据流：

```text
inputs -> M1 接入质检 -> M2/M3/M4/M5 处理 -> M6 融合/三维化 -> L0 汇总报告
                              └────────── M7 可选插件 ──────────┘
```

每次执行均先写入 `outputs/<run_id>/`，不修改 `inputs/`。质检失败的数据进入 `quarantine/`，并在清单中记录原因。

## 10. GUI 设计

主界面采用“项目工作区 + 模块标签 + 工具列表 + 参数面板 + 任务队列 + 结果/报告”工作台布局，不设置营销页。

- 顶部按功能模块分标签，模块名称不显示 M1-M7 前缀。
- 工具列表由 `ToolSpec` 生成，参数面板由 schema 动态渲染。
- 参数面板由 schema 动态渲染：输入目录、多选文件、数值、阈值、布尔开关。
- 任务队列显示运行状态、进度、日志和取消按钮。
- 结果视图先展示汇总结论，再展示每个文件明细，报告以 HTML 内嵌预览。
- 每个工具提供“干跑”按钮，执行前必须显示影响范围。
- 支持浅色和深色主题切换，深色主题采用接近 Codex 的黑色背景。
- GUI 实现位于 `dtdpgis/gui/`，启动脚本为 `DtdpGIS.pyw`，桌面快捷方式使用圆形图标。

## 11. 错误处理

- 单个文件失败不中断整个批处理，记录到 `ItemResult` 并继续。
- 可重试任务失败后按策略重试，达到上限后标记失败。
- 断点续跑依据 SQLite 中的任务状态恢复。
- GUI 层统一捕获异常，区分可恢复、可跳过、阻断性错误。
- 外部命令失败时保留完整 stdout/stderr 到运行日志。

## 12. 测试策略

- 每个工具提供小型合成数据夹具，覆盖正常、空数据、损坏文件、异常坐标四类输入。
- 坐标转换用已知控制点验证前后坐标，不允许只验证“不报错”。
- 拓扑修复验证面积、顶点数和相交关系变化。
- 栅格修复验证 Nodata 数量、边界和统计值。
- 平台层验证任务编排、重试、断点续跑和报告生成。
- 1.0 发布前用一批真实数据完成端到端验收。

## 13. 1.0 验收标准

1. 给定混合目录，可自动生成资产清单、质检结论和 HTML 报告。
2. 质检规则可通过 YAML 配置修改。
3. 批处理可取消、重试、跳过失败并断点续跑。
4. 所有输出写入独立 `run_id` 目录，不覆盖输入。
5. 新增一个符合接口的工具不需要修改 GUI 和 L0 平台。
6. 至少各有一个真实数据样例通过 M1、M2、M3、M4、M5 的端到端验证。

## 14. 里程碑

- P0：L0 平台底座 + M1 数据接入与质检，跑通完整报告链路。
- P1：M2 坐标与基准、M3 矢量清洗、M4 栅格修复、M5 点云 LAS 分支。
- P2：M6 融合与三维化、M5 OSGB 质量检测接口。
- P3：M7 插件机制与首个 AI 推理插件。

## 15. 风险与对策

| 风险 | 对策 |
|---|---|
| 克隆环境被破坏 | 只装 PySide6，不升级核心 GIS 包；保留环境快照说明 |
| OSGB/3D Tiles 转换复杂 | 1.0 只做质量检测，转换接入外部成熟工具 |
| AI 依赖冲突 | M7 使用独立环境，子进程调用 |
| 批处理大文件内存溢出 | 默认分块/流式读取，按需使用进程池 |
| 规则阈值项目间不一致 | 按项目 YAML 配置，不做全局写死 |
